  • 잘한 점: Vercel을 쓰되 클라우드 이전을 고려한 구조, GitHub Actions 주간 정적 데이터, Redis 캐시 구조

③ ChatGPT (종합 진단·로드맵, 가장 구체적)

  • 포지셔닝: “혼잡을 피해 이동하는 여행 도우미” — 전국 혼잡 포털·여행 종합 플랫폼보다 지금 가장 유리
  • 운영 사이트에서 직접 찾은 문제: 경복궁 단계 불일치(쾌적 vs 서울시 보통), ‘가장 한산한 시간’이 새벽 2시처럼 방문 불가 시간, 해운대 “예측 모델(샘플)”, 행사 전 축제의 현재 수치, 축제 혼잡이 시군구 전체 통계, /guide·/explore가 로봇에게 “불러오는 중…”, 마감된 체험 노출, 결제·약관·사업자 정보 미완
  • 데이터 계약: OFFICIAL_OBSERVED · OFFICIAL_FORECAST · MODEL_VALIDATED · RULE_BASED_ESTIMATE · HISTORICAL_AREA_PROXY · SAMPLE · UNAVAILABLE 로 품질 등급화, ‘실시간’은 실측에만
  • 추천: 후보 시간 = 운영시간 ∩ 입장 가능 ∩ 이용자 일정 ∩ 날씨, 불확실성 벌점
  • SEO/GEO: 핵심 목록 서버 렌더링, 메타·canonical·OG·JSON-LD, /methodology·/data-sources·/accuracy 공개, 예측 백테스트(MAE·등급 일치율), IP 강제 언어 전환 지양, 1,856곳을 한꺼번에 얇은 페이지로 만들지 말 것
  • 운영: /api/health·데이터 신선도, 크론 락·재시도, 레이트리밋, 오류 추적, E2E·Lighthouse CI
  • 수익: 결제보다 “검색 유입 → 시간·대안 확인 → 코스 저장 → 알림” 흐름 검증 먼저. KPI: 코스 완성률, 공유율, D7 재방문, 알림 활성화
  • 추가 기능 우선순위: ①운영시간 반영 추천 ②데이터 신뢰도 배지 ③가까운 한산한 대안 3곳 ④날짜별 비교 ⑤코스 저장·카톡 공유 … ⑫AI 대화형 플래너는 가장 나중

3. 코드로 확인한 사실 판정

3-1. 맞는 지적 — 고칩니다

지적코드 확인 결과조치
경복궁 단계 불일치장소 화면은 인원 기준 자체 점수, 서울 지역 화면은 서울시 공식 단계 → 같은 시각에 쾌적/보통이 다르게 나옴서울시 데이터가 있는 곳은 공식 단계를 기본 배지로 통일, 자체 값은 “자체 추정”으로 따로
가장 한산한 시간이 방문 불가 시간서울 지역 상세 FAQ가 12시간 예측 중 최솟값을 그대로 고름(새벽 포함). 장소 “언제 가면 좋을까요?”도 끝나기 직전 시각을 고를 수 있음운영 시간(없으면 08~22시) 안, 마감 1시간 전까지에서만 고르기
“예측 모델 (샘플)” 표기출처 라벨 문구가 CrowdView 예측 모델 (샘플)“CrowdView 추정 (요일·시간 패턴)”으로, 실측과 다른 배지
축제 혼잡 = 시군구 전체맞음 (데이터랩 시군구 방문객 비율)“지역 방문 증가 예상 (시군구 기준)”으로 이름 바꾸기, 행사 전에는 현재 수치 대신 “행사 전”
마감된 체험 노출‘접수중’ 상태만 보고 마감일은 안 봄마감일이 지난 건 빼기
/guide·/explore 로봇에게 빈 화면가이드 목록과 “더 많은 명소”를 브라우저에서 받아 그림첫 목록·총 건수·링크를 서버에서 그리기
레이트리밋 없음맞음Redis로 IP별 분당 제한
오류·신선도 감시 없음서버 운영 알림만 있고 브라우저 오류·데이터 신선도 점검 없음/api/health + 브라우저 오류 수집 + 오래된 데이터 표시
예측 정확도 미측정맞음예측 기록 → 다음 날 실측과 비교 → /accuracy 공개
방법론 공개 페이지 없음/llms.txt만 있음/methodology (출처·계산·한계)

3-2. 이미 되어 있는 것 (보고서는 원본 코드를 못 봄)

지적현재 상태
hreflang·canonical모든 페이지 pageMeta()가 5개 언어 + x-default 대체 주소와 canonical을 넣음, proxy가 Link 헤더도 붙임
robots·sitemaprobots.ts(AI 검색로봇 허용, 개인·운영 페이지 차단), sitemap.ts(장소·서울 119·가이드 2,755·축제·지역 여행)
구조화 데이터홈(WebSite·Organization), 장소·가이드·축제 상세에 JSON-LD(FAQ·Event 등) 있음 → TouristAttraction·BreadcrumbList 보강
공개 API CDN 캐시/api/public/crowd: s-maxage=300, stale-while-revalidate=300, 정적 데이터 /data/*.json은 force-static + CDN
서킷 브레이커·마지막 정상값lib/cached.ts가 원본 실패·한도 초과 시 Redis의 마지막 값 사용, 한도 90%에서 자동 정지
지도 SDK 지연 로딩지도 화면·지도 보기를 켤 때만 불러옴
모바일 하단 탭·safe-area·dvh하단 탭 4개(홈·지도·공항·마이), env(safe-area-inset-bottom), min-h-dvh 사용
색만으로 구분단계 배지에 글자(쾌적·보통…) + 막대 칸 수로 이중 표시. 지도 핀만 색 위주 → 보강
결제 멱등성결제 ID를 서버가 만들고 웹훅은 같은 결제를 두 번 처리하지 않음(이미 paid면 건너뜀), 금액·상태는 포트원 재조회
로봇 언어 전환검색·미리보기 로봇은 자동 언어 전환에서 제외, 모든 언어 주소에 직접 접근 가능

3-3. 동의하지 않거나 지금은 하지 않는 것

제안이유
Neon serverless 드라이버로 교체표준 pg + 함수당 작은 풀(max 5)로 충분하고 클라우드 이전에도 유리. 대신 Neon의 pooler 주소(-pooler)를 쓰도록 설정 안내
TanStack Query 도입클라이언트 조회가 몇 개뿐이고 대부분 서버·CDN에서 처리. 라이브러리보다 서버 렌더링 비중을 늘리는 쪽이 효과적
Redis Hash·GEO로 장소 저장장소 목록은 Redis가 아니라 정적 파일(CDN)에 있어 Redis 메모리 문제가 없음
IP 강제 언어 전환 폐지사이트 주인의 요구(해외 접속 = 그 나라 언어). 로봇은 이미 제외되어 색인 문제는 없음. 보완: 처음 방문 때만, 언어 선택은 쿠키로 유지, 화면에 언어 바꾸기 항상 표시
1,856곳 상세 페이지 한꺼번에ChatGPT 의견에 동의 — 얇은 페이지 대량 생성은 오히려 손해. 서울·공항·주요 축제 품질부터
다크 모드 지금디자인 전체를 다시 칠해야 해서 사용자 데이터 확인 후
환경변수 Vault 모듈지금 규모에선 과함. 환경변수 목록·켜짐 조건은 .env.example·설명서에 한 곳으로 정리돼 있음

4. 최종 실행 계획 (지금부터 순서대로 진행)

PR우선내용완료 기준
A. 데이터 신뢰성P0서울시 데이터가 있는 장소는 공식 단계로 통일 · 출처 라벨(실측/공식 예보/자체 추정/지역 통계) · ‘샘플’ 표현 제거 · 오래된 데이터 “갱신 지연” · 추천 시간은 운영 시간 안에서만 · 축제는 “지역 방문 증가 예상”, 행사 전엔 현재 수치 숨김 · 마감 체험 제외같은 장소 공식 단계 충돌 0, 운영 시간 밖 추천 0, ‘샘플’ 문구 0, 회귀 테스트
B. 검색로봇이 읽는 본문P0/guide 첫 목록·건수·링크와 /explore 더 많은 명소를 서버 렌더링 · 장소·서울 지역 상단에 단답 사실 문장 · TouristAttraction·BreadcrumbList JSON-LDJavaScript 없이 받은 HTML에 목록·링크·사실 문장이 있음

D. 신뢰 공개P1/methodology(출처·계산·한계) · 예측 기록 → 실측 비교 → /accuracy(등급 일치율·평균 오차)매일 정확도 숫자가 쌓이고 공개 페이지에 표시
E. 결정 돕기·공유P1가까운 한산한 대안 3곳 · 공유 코스 “이 코스로 나도 짜기”(담은 곳으로 복사) · 캘린더(.ics) 내보내기 · 코스에 비·미세먼지 경고상세 화면에 대안, 공유 → 복사 동작, .ics 다운로드
F. 성능·접근성P1관광공사·축제 사진 작은 썸네일 · 지도 핀에 단계 글자·aria · 핀 많을 때 묶기(클러스터) · 터치 영역 44px 이상홈 이미지 용량 감소, 지도 핀 400개에서도 부드러움

작업마다 브랜치 → PR → CI(타입 검사·테스트) 통과 → 머지. 끝나면 서비스 설명서 PDF와 인수인계 문서를 갱신합니다.
