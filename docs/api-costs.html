1한눈에 보는 결론

지금 월 비용은 약 2천 원도메인(월할 약 1,700원) + Papago 번역(월 수백 원 예상)이 전부입니다. 지도·Redis·QStash·메일·공공데이터는 무료 범위 안입니다.
출시하면 월 약 3만 원Vercel Pro $20(약 2만 8천 원)이 대부분입니다. Redis는 사용량에 따라 월 $1~2가 붙을 수 있습니다. 결제가 붙으면 결제 금액의 수수료가 따로 나갑니다.
공공데이터 호출 한도: 모두 30% 이하가장 빠듯한 건 인천공항 주차 정보(하루 최대 288회 / 1,000회, 29%)와 에어코리아(128회 / 500회, 26%)입니다. 사용자가 늘어도 이 숫자는 변하지 않습니다.

이번에 바꾼 것

  • 공공데이터 캐시를 Redis로 옮겼습니다. 전에는 Next.js 내장 캐시에 있어서, 나중에 직접 클라우드로 옮겨 서버를 여러 대 띄우면 서버마다 따로 호출했을 겁니다. 이제는 모든 서버가 Redis 하나를 같이 봅니다.
  • API별 하루 호출 수를 셉니다. 원본 API를 실제로 부를 때마다 Redis에 1씩 올립니다(캐시에서 읽은 건 세지 않음).
  • 한도 90%에 닿으면 자동으로 멈춥니다. 그날은 더 부르지 않고 마지막으로 받아 둔 데이터를 보여 줍니다. 공공데이터포털이 "한도 초과"라고 답해도 같은 처리를 합니다.
  • 매일 비용 리포트(PDF) 2쪽에 어제의 API별 호출 수와 한도 대비 %가 들어갑니다. 70%를 넘는 API가 있으면 디스코드·메일 본문에 경고가 붙습니다.
  • 에어코리아 미세먼지 캐시를 30분 → 1시간으로 늘렸습니다(측정값 자체가 1시간마다 바뀜, 한도 500회라 여유 확보).
  • "데이터 없음" 응답(공휴일 없는 달 등)도 30분 동안 기억해, 같은 걸 계속 다시 부르지 않게 했습니다.

2데이터를 가져오는 구조

식당 주방장이 아침마다 장을 봐서 냉장고(Redis)를 채워 두고, 손님(사용자)이 오면 냉장고에서 꺼내 줍니다. 손님이 100명이 와도 시장(외부 API)에 가는 횟수는 "몇 분마다 한 번"으로 정해져 있습니다.
[QStash, 10분마다] → /api/cron/refresh (수집기)
      ├─ 실시간: 인천공항 T1·T2 출국장, 한국공항공사 혼잡도, 서울시 도시데이터 (매번 원본 호출)
      └─ 결과를 Redis crowd:* 에 저장

[사용자] → CDN(60초) → 페이지 → Redis 에서 읽기만
                         └─ 날씨·공휴일·주차·축제 등: lib/cached.ts
                              메모리 → Redis(dg:*) → 원본(정해진 주기가 지났을 때만 1번)

캐시 3단계 (lib/cached.ts)

1
서버 메모리: 같은 서버가 방금 받은 값이면 바로 씁니다. Redis 명령도 안 씁니다.
2
Redis: 다른 서버가 받아 둔 값이 주기 안에 있으면 그걸 씁니다. 서버가 몇 대든 원본 호출은 주기마다 한 번입니다.
3
원본 API: 주기가 지났을 때만 부릅니다. 실패하거나 한도에 걸리면 Redis에 남아 있는 마지막 값을 씁니다(주기보다 6시간 이상 더 보관).

10분/30분처럼 주기를 API마다 다르게 둔 이유는 데이터가 바뀌는 속도가 다르기 때문입니다. 출국장 대기는 1분마다 바뀌어 10분, 미세먼지는 1시간마다 바뀌어 1시간, 생활인구는 월 단위라 하루 1번이면 충분합니다.

SA 관점"예약 수집 + 공유 캐시 + 호출량 계량" 패턴입니다. AWS로 옮기면 EventBridge Scheduler → Lambda(수집기) → ElastiCache(Redis), 호출량 계량은 같은 Redis 카운터 또는 CloudWatch 지표로 그대로 옮겨집니다. Next.js 전용 캐시에 기대지 않아서 코드 수정 없이 옮길 수 있습니다.

로컬에서 수집기를 직접 돌려 확인한 값

수집기를 두 번 연달아 실행했을 때 늘어난 호출 수: 인천 T1 +1, T2 +1, 한국공항공사 혼잡도 +2, 서울시 도시데이터 +6(장소 6곳)씩 늘었고, 캐시를 쓰는 나머지 API는 0회였습니다. 표의 "수집기" 줄 계산과 일치합니다.

출시 전 꼭: 운영계정 전환개발계정은 테스트용이라 한도가 작습니다. data.go.kr 마이페이지에서 서비스 화면 캡처와 함께 활용사례를 등록하고 운영계정 전환을 신청하면(무료) 인천공항 API는 하루 100만 건까지 늘어납니다. API마다 따로 신청합니다.

7한도 보호 장치와 매일 확인하는 법

1
캐시 주기로 하루 최대 호출 수 자체를 한도의 30% 이하로 묶어 둡니다 (3장 표).
2
호출 수 집계: 원본을 부를 때마다 Redis quota:날짜:API 를 1 올립니다. 8일 보관.
3
90% 자동 정지: 한도의 90%에 닿으면 그날은 원본을 부르지 않고 마지막 데이터를 씁니다. 화면에는 "n분 전 데이터"로 표시되고 사이트는 멈추지 않습니다.
4
"한도 초과" 응답 감지: 공공데이터포털이 LIMITED_NUMBER_OF_SERVICE_REQUESTS 오류를 주면 그날 남은 호출을 막습니다.
5
매일 09시 리포트: PDF 2쪽에 어제의 API별 호출 수·한도·사용률. 70%가 넘는 API는 디스코드·메일 본문 첫 줄 아래에 ⚠️로 표시됩니다.
경고가 오면① 그 API의 캐시 주기를 늘리거나(코드의 dataGoKr 세 번째 인자) ② 운영계정 전환을 신청하세요. 둘 중 하나면 해결됩니다.
