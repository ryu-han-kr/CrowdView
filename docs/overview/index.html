1. 한눈에 보기

서비스 정의

CrowdView는 공항·놀이공원·명소·축제·서울 주요 지역의 “지금 혼잡도”와 시간대별 예측을 보여 주고, 이를 바탕으로 덜 붐비는 시간·순서로 도는 여행 코스를 짜 주는 웹 서비스입니다. 한국어로 접속하면 혼잡도가 먼저, 해외에서 접속하면(IP 기준 자동 언어) 명소·축제 안내가 먼저 보입니다.

2. AI 검토 요청 프롬프트와 평가 기준

이 PDF를 다른 AI에 넣을 때 아래 프롬프트를 그대로 붙여 넣으면, 같은 형식의 답을 받아 서로 비교하기 쉽습니다.

당신은 (1) 여행·지도 서비스 제품 책임자, (2) 클라우드 솔루션 아키텍트, (3) 한국 시장 수익화 전문가 역할을 동시에 맡은 검토자입니다.
첨부한 "CrowdView 서비스 전체 설명서"를 끝까지 읽고 아래 형식으로 답해 주세요. 추측이 필요하면 "가정:"이라고 밝히고, 문서에 없는 사실을 지어내지 마세요.

1. 한 문단 총평 — 이 서비스가 누구의 어떤 문제를 얼마나 잘 푸는지, 가장 큰 강점 1개와 가장 큰 약점 1개.
2. 점수표 — 아래 8개 항목을 1~10점으로 매기고 각각 근거 2줄:
   제품 가치 / 국내 이용자 경험 / 외국인 이용자 경험 / 데이터 신뢰성(예측 정확도 포함) / 수익 모델 / 비용 구조 / 기술 구조·이식성 / 법적·운영 위험
3. 출시 전에 반드시 고쳐야 할 것 TOP 5 — 각각 "무엇을 / 왜 / 어떻게(구체적 방법) / 예상 작업량(시간) / 효과" 형식.
4. 3개월 안에 하면 좋은 개선 TOP 10 — 14장의 백로그와 겹치면 그 번호를 쓰고, 순서를 바꿔야 한다면 이유를 설명.
5. 수익화 제안 — Plus(월 3,900원)의 가격·혜택 구성, 외국인 단기권, 숙소 제휴, 광고의 균형. 숫자(전환율·단가 가정)를 넣어 월 매출 시나리오 3개(보수·기본·낙관).
6. 비용·확장 — 이용자 1천·1만·10만 명일 때 무엇이 먼저 병목/비용이 되는지와 대응.
7. UI/UX — 첨부 화면 캡처 기준으로 고칠 점 10개(화면 이름 + 구체적 수정안). 국내/외국인 이용자를 나눠서.
8. 예측·추천 알고리즘 — 7장의 방식에서 정확도를 높일 방법과 검증 방법(어떤 지표로, 어떤 데이터로).
9. 15장의 "결정해야 할 질문"마다 당신의 추천 답과 이유.
10. 내가 놓치고 있는 위험이나 기회 5개.

답은 한국어로, 표와 번호 목록을 써서 구체적으로. 일반론(예: "사용자 경험을 개선하세요")은 쓰지 말고 이 서비스에 맞는 실행 가능한 제안만.

평가할 때 지켜야 할 전제 (서비스 주인의 방향)

  • 1인 개발 (AI 코딩 도구 활용). 주인은 솔루션 아키텍트(SA)를 목표로 공부 중이라 특정 클라우드에 묶이지 않는 구조를 선호 — 지금은 Vercel이지만 나중에 직접 운영하는 클라우드(AWS 등)로 옮길 계획
  • 혼잡도와 기본 예측은 계속 무료, 시간을 아껴 주는 기능(알림·코스 전체·광고 제거)을 유료로
  • 모바일(768px 미만)은 앱처럼, PC는 웹 레이아웃. 디자인 참고는 야놀자(NOL): 큰 포토 배너, 아이콘 메뉴, 사진 카드, 은은한 파랑 그라데이션
  • 비밀 키는 코드·문서에 넣지 않음 (Vercel 환경변수 / GitHub Secrets)
  • 공공데이터는 하루 호출 한도의 30% 이하만 쓰도록 캐시 (사용자가 늘어도 원본 호출 수는 일정)

4. 화면별 기능

4-1. 홈 (/)

  • 큰 포토 배너: 4.5초마다 자동으로 넘어감(마우스를 올려도 계속), 점·화살표·밀어서 넘기기. 슬라이드: 인천공항 출국장 · 서울 실시간 119곳 · 오늘의 여행지 · 진행 중 인기 축제 · 한산한 코스 · Plus
  • 아이콘 메뉴 10개: 공항 · 테마파크 · 축제 · 서울 실시간 · 지역 여행 · 여행 가이드 · 추천 코스 · 체험·액티비티 · 내 주변 · 지도
  • 언어별 순서: 한국어 = 검색·파트 칩 → 지금 한산한 명소 → 뜨는 축제 TOP 5 → Plus 혜택 → 지역별 대표 명소 → 전체 장소 / 외국어 = 지역 명소 → 축제 → 한산한 명소 → Plus → 전체 장소
  • 지금 뜨는 축제 TOP 5: 2주 안 축제를 “작년 같은 기간 방문객 ÷ 평소” 비율로 순위
  • 전체 장소: 이모지 칩(전체·찜·명소·핫플·놀이공원·해변·공항·축제) + 한산한/붐비는 순 + 목록(세로 사진 카드)·지도 전환

4-2. 지역 여행 (/explore)

  • 17개 시도 칩 → 대표 명소(종류 칩: 역사·문화/자연/도시·거리/놀이·체험/바다), 그 지역 축제(60일), 더 많은 명소(관광공사 1,856곳, 20곳씩 더 보기)
  • 명소를 누르면: 우리 장소(1.5km 안) → 장소 상세, 서울 실시간 지역(0.8km 안) → 지역 상세, 그 외 → 지도(한국어 카카오맵, 외국어 구글 지도)
  • 목록 ↔ 지도 전환. 위에 붙어 따라오는 지역 칩

4-3. 서울 실시간 (/seoul, /seoul/{코드})

  • 119곳의 지금 인구(최소~최대)와 단계(여유·보통·약간 붐빔·붐빔), 붐비는/한산한/내 주변 순
  • PC는 왼쪽 정리 패널(상단 메뉴 아래로 따라옴): 검색 · 종류·혼잡 단계 체크박스 · “N개 고름” 요약 · ☆ 담은 곳 목록 + 코스 짜기 링크. 모바일은 칩 줄
  • 지역 상세: 12시간 예측, 연령·성별·거주/방문 비율, 근처 화장실·명소·맛집, 혼잡 알림 버튼, 근처 숙소 찾기

4-4. 서울 여행 가이드 (/guide, /guide/{id})

  • Visit Seoul 공식 다국어 정보 2,755곳 + 그 동네(1km 안 서울 실시간 지역) 지금 혼잡도
  • 거르기: 종류 · 구 · 그 동네 혼잡도 / 정렬: 기본순 · 한산한 순(맛집이면 “지금 덜 붐비는 맛집”) · 내 주변
  • 상세: 운영 시간·휴무·전화·지하철·홈페이지, 가까운 화장실, 근처 명소, 숙소 찾기(맛집 제외)

4-5. 한산한 코스 추천 (/route, 공유 /r/{id})

  • 입력: 출발지(내 위치·주요 10곳) · 출발 날짜(오늘~6일 뒤)·시각 · 일정(3·4·6·8시간) · 관심사(역사·문화/공원·자연/거리·쇼핑/놀이·체험) · 이동(대중교통/걷기) · ☆ 담은 곳 넣기
  • 출력: 최대 6곳 + 점심·저녁 맛집, 구간별 노선(예: 4호선 → 3호선)·분·km, 카카오맵 길찾기, 장소마다 이유(“하루 중 가장 한산한 시간에 도착”, “19시(매우 혼잡)를 피해서”, “10:00 개장까지 15분 기다려요”), 패턴 예측 표시
  • 여기서부터 다시 짜기, 공유 링크(30일 보관)

7. 계산 방식

7-1. 혼잡 점수 (0~100)와 단계

점수0~1920~3940~5960~7980~100
단계쾌적원활보통혼잡매우 혼잡

서울시 단계는 여유 25 · 보통 48 · 약간 붐빔 68 · 붐빔 88점으로 바꿈. 공항은 대기 인원·시간, 놀이공원은 놀이기구 대기, 그 외는 예측 모델(요일·시간·공휴일·날씨·관광공사 집중률)로 점수화. 실측이 아니면 화면에 “추정/예측” 표시.

7-2. 축제 혼잡 예측

관광공사 데이터랩 시군구 일별 방문자로 작년 같은 기간(같은 요일) 외지인·외국인 방문객 ÷ 그 전 4주 같은 요일 평균. 서울 축제는 장소 800m 안 서울 실시간 지역의 지금 인구.

7-3. 내일·주말 예측 (12시간 밖)

  • 가까운 지하철역(1.2km 안 2곳)의 요일 배수 × 시간대 비중: 시간대 = 지난달 역·시간대별 승하차(CardSubwayTime), 요일 = 최근 4주 일별 승하차(CardSubwayStatsNew). 예: 강남 일요일 54%, 홍대입구 토요일 122%
  • 그 지역의 지금 실시간·12시간 예측 점수와의 비율로 늘이거나 줄임. 월 자료가 평일 위주라 주말엔 출근(6~9시)·퇴근(17~19시) 꼭대기를 낮 수준으로 누름
  • 우리 장소는 장소별 예측 모델의 날짜별 예측. 화면에 “패턴 예측” 표시

7-4. 코스 추천 알고리즘

단계내용
후보우리 장소 + 서울 실시간 지역(역 주변 제외) 중 관심사가 맞고 출발지에서 대중교통 15km·걷기 3.5km 안. 서로 600m 안은 하나만. ☆ 담은 곳은 관심사·거리와 상관없이 먼저
이동시간1.2km 안 걷기(4.5km/h × 1.3 우회). 그 밖은 지하철 노선망 다익스트라: 역까지 걷기 + 기다림 4분 + 갈아타기 4분 + 내려서 걷기. 1~8호선은 실제 역간 시간, 다른 노선은 거리로 어림(38km/h, 공항철도 60km/h), GTX-A 제외. 역이 없으면 직선거리 어림(버스 포함 12분 + 18km/h)
비용 함수Σ(도착 시각 혼잡 점수 × 1) + 이동 분 × 0.8 + 개장 대기 분 × 0.4 + 같은 관심사 연속 8 + 식사 놓침 30
최적화욕심쟁이로 최대 6곳 고른 뒤 방문 순서 720가지를 모두 비교
제약일정 안에 끝내기, 운영 시간(그날 기준), 문 열기 90분 전까지 도착하면 기다림, 점심 11:20~12:40·저녁 17:20~18:40 시작 1시간(맛집 896곳 중 1.2km 안, 대표 메뉴 있는 곳)
설명그날(9~21시) 가장 한산한 시간 도착 / 피한 꼭대기 시각 / 개장 대기

한계: 버스 경로를 따로 계산하지 않음, 서울 중심(다른 지역 후보 적음), 예측 정확도 미검증 (13장).

8. 시스템 구조 · 이식성 · 품질 관리

[브라우저·PWA] ──> Cloudflare(DNS만) ──> Vercel Pro (icn1, Next.js 16 App Router, Node 런타임)
                                          ├─ 페이지: ISR(60초~1일) + CDN, 정적 JSON /data/*.json
                                          ├─ API: /api/route, /api/alerts, /api/plus/*, /api/portone/webhook, /api/admin/*, /api/public/crowd
                                          └─ Cron: 10분 수집기(/api/cron/refresh) · 매일 비용 리포트(/api/cron/cost-report)
                     Upstash Redis ── 실시간 혼잡 crowd:*, API 캐시, 하루 호출 수, 번역 캐시, 공유 코스(30일), 운영 알림 중복 방지
                     Postgres(Neon 예정) ── 회원·세션(Better Auth)·구독·결제·찜·담은 곳·푸시 구독·혼잡 알림 (migration 001~004)
                     GitHub Actions ── 주 1회 서울시·관광공사 정적 데이터 갱신(PR) · PR마다 타입 검사 + 테스트(CI)

이식성 (나중에 직접 클라우드로)

  • 외부 API는 lib/* 한 파일씩 감쌈 (fetch 기반, SDK 의존 최소). 결제도 포트원 REST 직접 호출
  • 캐시는 Next.js 전용 캐시가 아니라 Redis(표준 명령) → AWS로 옮기면 ElastiCache, Cron → EventBridge Scheduler, 수집기 → Lambda/컨테이너
  • DB는 표준 Postgres (Neon·Supabase·RDS 어디든), migration은 순수 SQL
  • 무거운 계산(코스·지하철)은 순수 함수 + 정적 데이터 → 서버 어디서든 같은 결과

품질 관리

  • TypeScript strict, PR마다 CI(타입 검사 + 테스트 20개: 코스·지하철·예측·결제 규칙·웹훅 서명)
  • 화면 문구는 t("한국어") + 번역 사전 4개 언어, 빌드 스크립트가 빠진 번역을 알려 줌
  • 모든 변경은 브랜치 → PR → 확인 후 머지. Vercel이 PR마다 미리보기 배포
  • 운영 알림(디스코드), 매일 비용·호출 수 리포트(PDF, 디스코드·메일)
